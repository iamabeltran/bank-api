## 2. Concurrency and idempotency: what the tests exercise

These are exact scenarios from the test suite, not measured throughput. Each assertion is exact.

| Test | Scenario | Result asserted |
|---|---|---|
| `TransferConcurrencyIntegrationTest` | 100 crossed transfers (A→B and B→A) from 16 threads, released together | 0 unexpected exceptions (a deadlock would surface as one); balances exactly 9,800 and 10,200 |

## 3. Local load test (k6)

Script: [`load-test/transfers.js`](../load-test/transfers.js). Setup: API running locally, MySQL in Docker,
up to 10 virtual users (10 s ramp-up, 40 s steady, 5 s ramp-down; 55 s in total). Each iteration is one transfer
of 1 MXN with a unique `Idempotency-Key`. Accounts start with 1,000,000 MXN.

| Scenario | Transfers | Transfers/s | p50 | p95 | p99 | Max | Errors |
|---|---|---|---|---|---|---|---|
| Spread: 10 accounts, random pairs | 14,683 | 264 | 26.6 ms | 67.7 ms | 97.3 ms | 1.08 s | 0.00% |
| Worst case: 2 accounts (all transfers contend for the same rows) | 7,077 | 129 | 68.1 ms | 110.6 ms | 131.4 ms | 155 ms | 0.00% |

How to read it:

- Both runs completed with **no failed request** and every transfer returned `201`.
- When every transfer targets the same pair of accounts, the row locks serialize them: throughput is about half and
  p95 latency rises from about 68 ms to about 111 ms. That is the cost of never losing or duplicating money.
- Figures cover the whole 55 s run, including ramp-up and ramp-down, and each scenario was run **once**. The 1.08 s
  maximum in the spread run is most likely JVM warm-up, since it was the first load the API received.
