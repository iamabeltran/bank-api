## 2. Concurrency and idempotency: what the tests exercise

These are exact scenarios from the test suite, not measured throughput. Each assertion is exact.

| Test | Scenario | Result asserted |
|---|---|---|
| `TransferConcurrencyIntegrationTest` | 100 crossed transfers (A→B and B→A) from 16 threads, released together | 0 unexpected exceptions (a deadlock would surface as one); balances exactly 9,800 and 10,200 |
| `TransferConcurrencyIntegrationTest` | 100 concurrent transfers of 10 from an account holding 500 | Exactly 50 succeed and 50 are rejected; balance ends at 0 |
| `TransferConcurrencyIntegrationTest` | 300 random transfers among 5 accounts (fixed seed) | Total money conserved; no negative balance |
| `TransferIdempotencyIntegrationTest` | 20 parallel requests with the same `Idempotency-Key`, funds for only one | 1 executed, 19 replayed, 1 distinct ledger id, 0 failures |
| `TransferIdempotencyIntegrationTest` | Same key, different amount | Rejected (`422`); balances untouched |

```powershell
mvn clean verify                                   # tests + coverage report

docker compose up -d
mvn spring-boot:run                                # leave it running in its own terminal
k6 run load-test\transfers.js
k6 run -e ACCOUNTS=2 load-test\transfers.js
```
